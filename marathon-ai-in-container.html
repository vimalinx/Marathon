Marathon · In-Container Agent Runtime

AI 现在是怎么在容器里跑起来的

现在这套系统不是“宿主机上的 AI 去远程操纵容器”，而是 AI 主循环本身就在容器里面运行。 宿主机只做准备容器、同步 agent 文件、启动进程、镜像日志和提供 Web UI 控制面。

AI 主体在容器内 唯一工具是命令执行 每轮都写日志 宿主机只围观 + 控制

一句话链路

先准备容器，再把 agent 放进去，然后在容器里自己循环。

Web UI / script
  -> host.orchestrator
  -> lxc-attach into container
  -> start python3 /opt/marathon/agent_loop.py
  -> agent_loop calls model
  -> agent_loop calls agent_tools
  -> command runs in /workspace/sandbox
  -> round logs written to /workspace/runtime-log/<run_id>
  -> host mirrors logs back to runs/<run_id>
容器内主循环
agent_loop
文件是 container/agent_loop.py，同步进容器后放在 /opt/marathon/agent_loop.py。
容器内唯一工具
agent_tools
AI 只会得到一个工具：执行一条命令，并拿回 JSON 结果。
真正工作目录
sandbox
命令默认在 /workspace/sandbox 里跑，这也是 agent 真正修改文件的地方。
轮次日志目录
runtime-log
每个 run 会写到 /workspace/runtime-log/<run_id>/，宿主机会镜像回来。

完整启动流程

从点按钮到 AI 真正在容器里执行命令，中间大致会经过这几步。

1

准备基础容器

通过 scripts/create_base_container.sh 创建 base 容器。 这一步会装好 python3、git，创建 /opt/marathon、 /workspace/sandbox、/workspace/runtime-log。

2

把 agent 文件同步进容器

Web UI 或启动脚本会把本地的 container/agent_loop.py、 container/agent_tools.py 和 prompts/minimal_system.txt 写进容器的 /opt/marathon/。

3

宿主机启动容器内 agent 进程

host/orchestrator.py 用 sudo -n lxc-attach 进入容器， 然后用一个 Python launcher 在容器里 subprocess.Popen(['python3', '/opt/marathon/agent_loop.py'])。

4

agent_loop 在容器里无限轮询

主循环读取 prompt、采集 sandbox 状态、拼消息、调用模型、解析动作、执行工具、写 round 日志、提交 sandbox git。

↓
5

模型返回下一步动作

模型被要求只输出一个 JSON 对象，至少包含 summary、argv、timeout。

6

agent_tools 执行命令

agent_loop 并不直接 subprocess.run 用户动作， 它会调用 agent_tools.py，由工具在 /workspace/sandbox 执行命令并返回 JSON。

7

容器内写回 round 产物

每轮都会生成 request.json、response.txt、 action.json、tool_result.json、state_before.json、 state_after.json 等文件。

8

宿主机同步镜像日志

宿主侧 orchestrator 会持续把关键文件从容器里拷回 runs/<run_id>， Web UI 再读这些文件来展示状态、最近动作、最近轮次和实时轨迹。

容器里到底有什么

AI 真正依赖的是下面这些路径。

路径 作用
/opt/marathon/agent_loop.py AI 的主循环程序，负责每轮调模型、解析动作、执行工具、写日志。
/opt/marathon/agent_tools.py AI 唯一能直接调用的外部能力，执行一条命令。
/opt/marathon/minimal_system.txt system prompt，被容器内主循环读取。
/workspace/sandbox AI 真正工作的目录，命令默认在这里执行，文件修改也落在这里。
/workspace/runtime-log/<run_id> 每轮运行的日志、状态、动作、模型回复和 live stdout/stderr。
/workspace/sandbox/.git 容器内 sandbox 自己有 git，AI 每轮动作后会 commit 当前沙盒状态。

容器外的配合方

AI 虽然在容器里跑，但容器外还有两个关键角色。

宿主机 orchestrator

负责启动容器内 agent、写 STOP 信号、同步日志、做宿主镜像提交。

Web UI

负责管理容器和 run。它不直接替 AI 思考，只是发起启动并读取镜像出来的状态文件。

模型接口

容器本身要能访问模型 API，因为调用模型的是容器内的 agent_loop.py，不是宿主机。

每一轮 inside-container loop 在做什么

这是最关键的部分。你如果想理解“AI 怎么在容器里跑”，核心就在这里。

轮开始前

采集当前状态

扫描 sandbox 文件树、读取 sandbox git status，同时把 prompt、tool 源码、loop 源码都读出来。

拿最近反馈

读取上一轮的 latest_action.json 和 latest_tool_result.json，再取最近几轮 events。

拼消息给模型

system 是 prompt 文件，user 内容是一个 JSON 包：当前轮次、任务提示、最近几轮、上次动作、上次工具结果、当前 sandbox 状态。

轮执行中

调用模型

向 /chat/completions 发请求，模型配置里可以带 reasoning_effort、temperature 等。

提取 JSON 动作

如果模型没有干净地只输出 JSON，主循环会尝试从文本里抽出一个 JSON object。

执行工具

把动作 JSON 丢给 agent_tools.py，由它在 sandbox 执行 argv。

↓

轮结束时

再次采集状态

得到 state_after，这样系统能知道这轮命令前后沙盒和 agent 自己有没有变化。

写 round 文件

把 request、response、action、tool result、before/after state 全写入当前 round 目录。

更新 live 文件

例如 latest_action.json、latest_tool_result.json、latest_response.txt。

轮提交与状态更新

写 events.jsonl

记录 round_completed 或 round_failed 事件，给宿主和 UI 看。

提交 sandbox git

每轮会对 /workspace/sandbox 做一次 git commit，这样 agent 的工作区变更是轮次化的。

更新 status.json

记录当前状态、完成轮数、最后摘要、最后命令返回码等。

关键文件各自扮演什么角色

你如果要继续改这个项目，这张表最有用。

文件 角色 你改它会影响什么
scripts/create_base_container.sh 初始化 base 容器 影响容器里预装什么、网络怎么配、初始 sandbox 长什么样。
scripts/start_run.sh 快速复制容器并启动一次 run 影响“命令行启动一次实验”的体验。
host/orchestrator.py 宿主侧 supervisor 影响容器内进程怎么被启动、怎么同步日志、怎么处理 STOP。
container/agent_loop.py 容器内 agent 的脑干 影响每轮 prompt、状态采样、模型调用、结果解析和 round 日志格式。
container/agent_tools.py 容器内唯一工具 影响 agent 允许执行什么、在哪执行、结果如何返回。
host/web_ui.py 宿主 Web 控制面 影响页面能不能创建 run、查看状态、停止任务和观察轨迹。

为什么这叫“AI 在容器里跑”，不是“容器里只有工作区”

这两种架构差别很大。

调用模型的是容器内进程

不是宿主机拿到模型结果后再去替容器执行命令。

执行命令的是容器内工具

agent_tools.py 运行在容器里，默认 cwd 是 /workspace/sandbox。

主循环源码本身也在容器里

它甚至可以读到自己的源代码和工具源码，系统还专门跟踪这些源码有没有被 agent 改动。

坏掉的是这个 run 容器，不是整个宿主链路

这正是实验平台想要的边界：agent 可以把自己搞坏，但最好只坏在这个容器里。

当前这条链路最脆的地方

知道它怎么跑，也要知道它在哪最容易断。

1 模型输出 JSON 不稳定

如果模型回复不是干净 JSON，主循环可能直接失败。这是现阶段 inside-container loop 最现实的中断点。

2 容器必须能访问模型 API

因为调用模型的是容器内进程，不是宿主机，所以网络一断就不是“观测不到”，而是 agent 根本跑不动。

3 宿主依赖 LXC / sudo / bridge

容器怎么建、怎么起、怎么 attach，全部依赖宿主机这套环境。

4 agent 可以修改自己

这是实验功能，也是风险点。它可以把 agent_loop.py 或 agent_tools.py 改坏。

最后一句总结

如果你只想抓住主线，就记下面这句话。

Marathon 现在的运行方式是：
宿主机先准备容器并把 agent 文件同步进去，
然后在容器里启动 python3 /opt/marathon/agent_loop.py。

从那一刻开始：
- 调模型的是容器里的 agent_loop
- 执行命令的是容器里的 agent_tools
- 真正被修改的是容器里的 /workspace/sandbox
- 真正被记录的是容器里的 /workspace/runtime-log/<run_id>
- 宿主机只负责同步镜像、展示 UI、发停止信号和管理容器生命周期
