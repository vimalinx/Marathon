我根据代码库推断，你真正想要的是什么

这不是从想象推，而是从 README、模块职责和 UI 信息架构反推。

1. 一个能把 AI 真正放进沙盒里运行的自治实验环境

不是宿主机遥控容器，而是 agent 自己在容器里读 prompt、调模型、执行命令、修改自己。

2. 一个可观测、可回放、可对比的宿主机控制面

你想看的不只是“最后结果”，而是每轮动作、stdout/stderr、状态前后差异、自修改痕迹。

3. 两种实验路径

一条在 LXC 沙盒里做强隔离探索，一条直接在真实 Git 仓库里做 nightly 自动迭代。

4. UI 不只是运维面板，而是“浏览式实验台”

最近的 dashboard 设计文档明确在把首页从控制台感改成浏览器感，但核心仍然围绕 agent 运行状态。

5. 允许 agent 自我修改，是产品定义的一部分

系统主动跟踪 `prompt_source`、`tool_source`、`loop_source` 的变化，说明“观察自修改”不是偶然功能，而是核心研究目标。

当前代码是怎么实现的

把主链路拆开看，整个系统其实非常清晰。

1. 容器内 Agent Loop

container/agent_loop.py 每轮收集沙盒状态、最近动作和工具结果，拼成消息发给模型，再提取 JSON action。

核心：单轮闭环

2. 唯一工具层

container/agent_tools.py 只做一件事：在 sandbox 目录执行一条命令，把结果打包成 JSON。

核心：单工具、强约束

3. 宿主 Supervisor

host/orchestrator.py 负责同步 prompt、启动 agent 进程、轮询状态、镜像日志和最新 round 到宿主 runs/。

核心：镜像与控制

4. Web UI / API

host/web_ui.py 用标准库 HTTP server 暴露静态页面与 API，管理容器、run、模型配置和 prompt。

核心：宿主控制面
↓

5. 状态与运行镜像

state/containers/ 保存容器元数据，runs/ 保存 host 镜像，host-runs/ 保存 nightly 运行日志。

核心：文件驱动状态

6. UI 页面分层

首页看重点与最近活跃；/new 创建任务；/container 看单容器实时轨迹；/sandboxes 管理容器。

核心：浏览式控制台

7. Host Nightly

host/host_nightly_runner.py 直接对真实仓库跑 round，必要时 checkpoint 脏工作区，并创建 nightly 分支。

核心：真实仓库自动迭代

8. Design Lab

设计实验室是 UI 变体观察台，用于比较不同界面布局，并不阻塞核心运行链路。

旁支：界面实验

它还缺什么，才算“真正能跑起来”

这里说的不是“代码能 import”，而是“作为系统能稳定工作”。

1
一套可重复的宿主环境 bootstrap

现在真正的复杂度在 LXC、bridge、veth、免密 sudo、tmux、容器内 apt。缺少“一键把宿主环境准备好”的正式流程。

2
更强的模型输出协议与修复策略

真实样本已证明：只要 JSON 输出破一点，run 就会失败。需要响应修复、重试、结构化输出约束或备用解析策略。

3
更可靠的失败恢复与续跑

目前更像“失败即结束”。缺少从上轮状态恢复、自动插入纠错提示、按错误类型重试等能力。

4
安全收口

模型配置里明文保存 API key，本地 UI 无认证，容器和宿主操作权限较高，这些都不适合长期使用。

5
真正围绕“任务完成”设计的反馈闭环

现在系统主要让你看到 agent 正在做什么，但还较少判断“它有没有接近成功定义”。

6
更真实的端到端环境测试

91 个测试很好，但多数仍是单元/轻集成。真正依赖的 LXC 与宿主条件，需要更系统的 smoke/e2e 证明。

最关键的风险矩阵

不是所有缺口都同级，下面是我认为最值得优先补的四项。

P0 密钥明文落盘

state/model_profiles.json 当前保存 API key。即使这是本机工具，也应该改成 env-only、引用式配置或最少脱敏存储。

P0 模型 JSON 响应脆弱

长跑真实失败已经落在这里。只要不修，这个平台的稳定性天花板就不高。

P1 环境依赖太多且隐式

机器稍微不一样，bridge/veth/modules/sudo 就可能出问题。当前更像作者机器上的可运行系统。

P1 过度偏向观察，尚未偏向产出

你现在已经很会看 agent 做了什么，但还不够会保证 agent 做成了什么。

我建议的下一步顺序

如果你的目标是把它从“研究原型”推进成“可靠可用系统”，优先级应该这样排。

优先级 建议动作 为什么
P0 把模型输出层改成更稳的结构化协议 这是已被真实 run 证明的第一稳定性瓶颈。
P0 移除明文 API key 持久化，改为 env 或安全引用 这是明显的安全债，不该继续累积。
P1 做一份宿主环境 preflight + bootstrap 把 LXC、bridge、sudo、tmux、git 前提显式化，降低“只在作者机器可跑”的风险。
P1 做端到端 smoke：建容器 → 启动 run → 完成 3 轮 → UI 可见 目前测试多，但缺少完整主链路的自动验证。
P1 补失败恢复与自动纠错轮 否则一旦响应异常就直接停，长跑稳定性很难上去。
P2 给 UI 增加“成功定义 / 任务完成度”视角 把控制台从“看轨迹”推进到“看结果”。
P2 明确 design-lab 与主产品节奏的关系 否则 UI 实验支线会持续消耗主线注意力。
