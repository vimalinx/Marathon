# Releasing

## `v0.1` Release Checklist

1. Ensure the repository is clean enough to identify intended release changes.
2. Run the release readiness script:

```bash
./scripts/check_release_ready.sh
```

3. Run the full test suite directly if you need an explicit standalone proof:

```bash
python3 -m pytest -q
```

4. Confirm README instructions still match the current startup flow.
5. Confirm no real credentials or local environment files are staged.
6. Update [CHANGELOG.md](./CHANGELOG.md).
7. Update or review the release notes document for the target version.
8. Create the release tag.

Example:

```bash
git tag -a v0.1.0 -m "Marathon v0.1.0"
git push origin v0.1.0
```

## GitHub Release Contents

For a basic public release, include:

- version tag
- summary paragraph
- highlights list
- setup notes
- known limits

The first release notes draft lives in:

- [docs/plans/2026-04-06-v0.1.0-release-notes.md](./docs/plans/2026-04-06-v0.1.0-release-notes.md)
- [`.github/release.yml`](./.github/release.yml) configures GitHub's autogenerated release-note grouping if you choose to use it

## Recommended Publish Sequence

1. Verify tests.
2. Review changelog and release notes.
3. Create and push the version tag.
4. Create the GitHub Release using the release notes draft.
5. Mark experimental surfaces explicitly in the release description if they are mentioned.

## Notes

- `Marathon Core` is the primary supported release surface for early public releases.
- `Marathon Site` and `design-lab` remain more experimental unless explicitly promoted in release notes.
